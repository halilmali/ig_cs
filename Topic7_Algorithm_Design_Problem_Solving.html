Learning Objectives — The Program Development Life Cycle

By the end of this section you should be able to:

  • Understand the program development life cycle: analysis → design → coding → testing
  • Understand sub-systems: a computer system is made of sub-systems, made of further sub-systems

7.1

The Program Development Life Cycle

All programs are created through four stages in a fixed order. The cycle is usually iterative — testing often feeds back into earlier stages when errors are found.

Analysis → Design → Coding → Testing — with testing feeding back into earlier stages (iterative cycle)
Exam Tip: the four stages must be listed in this order. Mention that testing can cause a return to earlier stages (e.g., redesign or recode).

Stage 3: Coding

This stage involves writing the actual program code, based on the design produced in Stage 2.

✍️ Translating the design

The programmer converts the structure diagram / flowchart / pseudocode into a high-level language (e.g., Python, Java).

🔄 Iterative testing

Code should be tested in small sections as it is written — not left until the entire program is complete. This finds errors early, when they are easier to fix.

# small sections are tested as they are written # e.g. check one function works before writing the next def add_scores(scores): # tested straight away total = 0 for s in scores: total = total + s return total
Exam Tip: "iterative testing" means testing while coding — say it, don't just describe testing at the end.

7.1

Stage 4: Testing

Testing involves running the finished program with test data to check it behaves as expected and to identify and correct errors before the solution is complete.

✅ What is checked

  • Correct outputs for valid (normal) data
  • Graceful rejection of invalid data
  • Edge cases — extreme & boundary values
  • Programs never crash on unexpected input

🔍 How errors are handled

  • Errors found are corrected
  • The program is re-tested
  • This may mean revisiting design or coding (the cycle loops)
Note: detailed testing — the four types of test data (normal, abnormal, extreme, boundary) — is covered in Section 7.4.

7.1 · Program Development Life Cycle9 / 43
7.1

Decomposing a Problem

Decomposition is the process of breaking a large, complex problem down into smaller, simpler parts (sub-problems) that are easier to understand, design, and solve individually.

🎯 Smaller = clearer

Each sub-problem has a single, focused task — much easier to design and code.

🧩 Teamwork

Different parts can be built separately and later combined into the whole solution.

🛠️ Easier testing

Each sub-problem can be tested independently before integration.

Worked example

Decomposing "plan a birthday party"

  • Guests — create the list, send invitations, track replies
  • Food — choose menu, order supplies, arrange cooking
  • Venue — book the hall, arrange chairs and tables
  • Entertainment — book music, plan games, arrange prizes

Each of these can be broken down further — e.g. "track replies" needs recording who said yes, who said no, and who hasn't replied.

7.1 · Program Development Life Cycle10 / 43
7.1

Worked Example: Decomposition

Problem: "A program to manage a library's book loans." Decompose it into component sub-tasks.

Step-by-step decomposition
  1. Add a new book — enter book details (title, author, ISBN) into the catalogue
  2. Register a member — capture member details and issue a library card number
  3. Issue a loan — record which member has borrowed which book and when
  4. Return a book — remove the loan record and update the book's availability
  5. Calculate overdue fines — compare return dates, compute fines for late returns
Why decompose? Each sub-task above is a manageable module that can be designed, coded and tested separately — then combined into the complete library system.

Designing a Solution: Flowcharts and Pseudocode

As well as structure diagrams, the design stage uses flowcharts and pseudocode to plan the logic of a solution before coding begins.

📐 Flowcharts

Standard symbols connected by arrows showing the sequence and decisions of an algorithm:

🟩 START / STOP ⬜ PROCESS ◆ DECISION ▨ INPUT / OUTPUT

Flowchart symbols are covered in detail in Section 4 (and 8) of the syllabus.

7.1

Explaining the Purpose of an Algorithm

How to answer "explain the purpose of a given algorithm" exam questions:

Part of answerWhat to do
State the overall purposeWhat the algorithm is designed to achieve — e.g. "this algorithm calculates the average of a list of numbers".
Describe the processes involvedWhat the algorithm actually does, step by step — e.g. "it totals all the values in a loop, counts them, then divides the total by the count".
Worked example

Explain the purpose of this algorithm

total = 0 count = 0 INPUT n WHILE n <> -1 DO total = total + n count = count + 1 INPUT n ENDWHILE OUTPUT total / count

Purpose: reads numbers until -1 is entered (the sentinel value), totals them, counts how many were entered, then outputs the average.

💡Exam Tip: read the algorithm carefully line by line before answering — identify what each variable represents and how it changes as the algorithm runs.

7.2 · Standard Methods of Solution16 / 43
7.2

Linear Search

A linear search checks each item in a list one by one, in order, from the beginning, until the required item is found or the end of the list is reached.

Check 12 ✗ → check 5 ✗ → check 42 ✓ — found at position 3
When to use it: simple to implement and works on unsorted lists — but slow for very large lists because items may have to be checked one at a time.
7.2 · Standard Methods of Solution17 / 43
7.2

Bubble Sort

Bubble sort compares each pair of adjacent items, swapping them if they are in the wrong order, and repeats passes through the list until no more swaps are needed.

Worked example — sort [5, 1, 4, 2] ascending
Start: [5, 1, 4, 2] Pass 1 — compare adjacent pairs, swap if out of order: 5>1 → swap → [1, 5, 4, 2] 5>4 → swap → [1, 4, 5, 2] 5>2 → swap → [1, 4, 2, 5] Pass 2 — repeat from the start: 1<4 → keep → [1, 4, 2, 5] 4>2 → swap → [1, 2, 4, 5] 4<5 → keep → [1, 2, 4, 5] Pass 3 — no swaps needed → list is sorted: [1, 2, 4, 5]
Key points: each pass moves the largest remaining value to its final position; the process stops early when a complete pass produces no swaps.
7.2 · Standard Methods of Solution18 / 43
7.2

Totalling and Counting

Two closely related techniques that use a variable updated inside a loop:

TechniqueHow it worksExample
TotallingA variable (a "running total") is increased by adding a value to it each time a loop repeats, building up a sum.Total of all sales entered during the day
CountingA variable (a "counter") is increased by 1 each time a loop repeats, counting how many times something occurs.Counting how many valid entries were submitted

➕ Totalling pattern

total = 0 FOR each value DO total = total + value ENDFOR

🔢 Counting pattern

count = 0 FOR each item DO IF condition THEN count = count + 1 ENDIF ENDFOR
Exam Tip: never forget to initialise the total/counter to 0 before the loop — a classic lost mark!
7.2 · Standard Methods of Solution19 / 43
7.2

Finding Maximum and Minimum Values

Process: set a variable to the first value in the list, then compare each subsequent value against it — replacing the stored value whenever a larger (for maximum) or smaller (for minimum) value is found.

Finding the maximum
max = first value FOR each next value DO IF value > max THEN max = value ENDIF ENDFOR OUTPUT max
Finding the minimum
min = first value FOR each next value DO IF value < min THEN min = value ENDIF ENDFOR OUTPUT min
Only difference: the comparison operator — > for maximum, < for minimum. Everything else is identical.
7.2 · Standard Methods of Solution20 / 43
7.2

Finding the Average Value

The average combines the two techniques from earlier slides:

Use totalling to add up all values, counting to find how many there are, then divide total by count
Worked example

Scores: 45, 78, 92

Total = 45 + 78 + 92 = 215  ·  Count = 3  ·  Average = 215 ÷ 3 = 71.67 (to 2 d.p.)

Watch out: if you divide before the loop finishes, or count zero items, the answer will be wrong — divide after the loop completes.

Quick Check — Standard Methods of Solution

Q4. Describe how a linear search works.

Answer: Each item in the list is checked one by one, in order, from the beginning, until the required item is found or the end of the list is reached.

Q5. Describe the steps of a bubble sort.

Answer: Adjacent pairs of items are compared and swapped if they are in the wrong order. This is repeated in passes through the list until a complete pass produces no swaps — the list is then sorted.

Q6. Explain how a program can find the maximum value in a list of numbers.

Answer: Set a variable to the first value. For each subsequent value, if it is greater than the stored variable, replace it with the new value. After checking all values, the variable holds the maximum.

7.3 · Validation and Verification23 / 43
7.3

Why Validate Data?

Validation is an automated check performed by the computer to ensure that input data is sensible, reasonable, and meets pre-set criteria before it is accepted — helping to maintain data integrity.

🧮 Range

Age 0–120, percentage 0–100

📏 Length

Password ≥ 8 characters

🔤 Type

Age must be an integer, not text

Critical limitation: validation cannot check if data is actually correct or true — only that it is reasonable. A valid age of "25" could still be a typing error for "52".
Example

A booking form accepts a date

A date of 31/02/2025 can pass a format check (it looks like a date) but is not a real date — a range check on the day of the month helps catch it. Validation makes the data more likely to be right, but never guarantees it.

Why Verify Data?

Verification is the process of checking that data has been copied or transferred accurately from one location/source to another — without being changed or corrupted.

Verification compares the entered data against the original source to catch transcription errors
Example: a data-entry clerk types names from a paper form into a computer — verification checks the typed names match the paper form exactly.

7.4 · Test Data31 / 43
7.4

Why Test With Different Data Types?

A range of test data types is used to thoroughly check that a program works correctly under all circumstances — including data that should be accepted and data that should be rejected.

✅ Normal

Typical valid data the program should accept.

❌ Abnormal

Invalid data the program should reject.

⚡ Extreme

The largest / smallest values that should still be accepted.

🎯 Boundary

The value just inside AND just outside each limit of the accepted range.

Why bother?

Testing only "normal" data hides bugs

A program accepting ages might crash on -3 or accept 999 if only sensible values are tested. Testing with abnormal, extreme and boundary data reveals these faults.

Link to 7.1: choosing good test data is part of the testing stage of the program development life cycle.

7.5

What is a Trace Table?

A trace table is used to perform a "dry run" of an algorithm — manually following its logic step by step, without running it on a computer — recording the values of variables, outputs, and user prompts at each stage.

A trace table documents what happens to every variable as the algorithm runs, line by line
Why trace tables? They reveal logic errors (e.g. a loop running one too many times) that might be invisible when just reading the code.
7.5 · Trace Tables & Errors37 / 43
7.5

How to Set Up a Trace Table

  1. Identify every variable used in the algorithm and create a column for each.
  2. Add extra columns for any outputs produced and any user prompts / inputs.
  3. Work through the algorithm one line / step at a time, in order.
  4. Record a new row each time a variable's value changes.
Example columns for a simple loop
ntotalOUTPUT
30
33
58
88

Each column = one variable. New row only when a value changes — unchanged variables are left with their previous value (or blank if not yet set).

💡Exam Tip: precision matters — write exact values in each cell. Leave a cell blank if a variable has not yet been given a value at that point.

7.5

Worked Example: Completing a Trace Table

Algorithm: total three entered numbers and output the total. Test data: 5, 8, 3.

Pseudocode
total = 0 FOR count = 1 TO 3 INPUT number total = total + number ENDFOR OUTPUT total
Completed trace table
countnumbertotalOUTPUT
150 → 5
285 → 13
3313 → 16
41616

After count = 4 the loop ends (4 > 3) and the final OUTPUT total runs.

Reading the trace: "5 → 13" shows the total before → after updating. In an exam table you would write just the new value (13) or follow the layout requested in the question.
7.5 · Trace Tables & Errors39 / 43
7.5

Identifying and Correcting Errors

How to approach "identify the error" exam questions:

  1. Perform a dry run using a trace table — see where the output does not match the expected result.
  2. Check for common logic errors: incorrect comparison operators, incorrect loop boundaries, or variables not being reset / initialised.
  3. Suggest a specific correction — e.g. changing x > y to x >= y — rather than a vague description of the problem.
Worked example — find the error
total = 0 FOR i = 1 TO 5 total = total + i # expected total 15 ENDFOR

Trace shows: 1+2+3+4+5 = 15 ✓ … but wait — what if the code was i < 5 in the loop condition? Then it runs 1..4 = 10 — incorrect. Correction: change i < 5 to i <= 5 (or i < 6).

💡Exam Tip: precision is required — writing x > y is acceptable, but writing "x is greater than y" is not an acceptable way to express algorithm logic.

7.5

Writing and Amending Algorithms

Algorithms for given problems must be written or amended using the three required representations: pseudocode, program code, and flowcharts.

📝 Pseudocode

Structured plain-language logic. Detail and syntax covered in Section 4 / 8.

💻 Program code

Real code in a high-level language (e.g. Python, Java, VB).

📐 Flowcharts

Standard symbols (terminator, process, decision, input/output) linked by arrows.

Amend example

"Amend the algorithm so it also outputs the average"

# original: total = total + number # inside loop # amended — add after the loop: average = total / count OUTPUT average
Strategy: draw on the standard methods of solution from Section 7.2 (totalling, counting, max/min, average, linear search, bubble sort) — most questions reuse these patterns.
